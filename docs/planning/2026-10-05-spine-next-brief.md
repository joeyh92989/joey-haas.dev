## Scope, in order

**A. The nightly job (backend + workflow)**

1. `JOB_TOKEN`: an optional env var (`config.py`, `_optional`), declared in `render.yaml` with `sync: false`. Unset means every job request is a 401 and the site behaves exactly as today.
2. `require_admin` (`items.py`) also accepts `Authorization: Bearer <JOB_TOKEN>`, but **only** when `(request.method, request.url.path)` is in a module-level `JOB_ROUTES` whitelist: `POST /api/picker/next`, `POST /api/physical/refresh-registry`, `POST /api/physical/refresh`, `POST /api/physical/refresh-switch1`, `POST /api/physical/resolve`, `POST /api/recommendations/generate`, `GET /api/physical/status`. Compare with `secrets.compare_digest`. Tests pin the whitelist: the token on a listed route passes; the same token on `PATCH /api/items/{id}` and `POST /api/items` is a 401; a wrong token, and no token configured, are 401s; nothing changes for a session. Decide in the design how the dependency reaches the token (app state set in `main.py`, or a dependency built in `main.py` and handed to the routers) — `require_admin` is imported by four routers today, so prefer the shape that leaves their signatures alone.
3. `.github/workflows/nightly.yml` replaces `snapshot.yml` (one workflow; keep `workflow_dispatch`, add a boolean input `discover` to force a batch). Cron `17 0 * * *` (18:17 Denver in summer, 17:17 in winter; off the hour as today). Steps, each a `curl` with the bearer header and a timeout long enough for the step (the store walk is the slow one; the importer note in `CLAUDE.md` says Render allows 100 minutes):
   - wake `/api/health` — the existing loop, unchanged;
   - `POST /api/picker/next` with `{}` — three picks recorded as shown; the public route publishes them after the next UTC midnight, so each run publishes yesterday's and records today's. Say so in a comment;
   - `POST /api/physical/refresh-registry`; `POST /api/physical/refresh` (all stores); on Sundays `POST /api/physical/refresh-switch1`; then `POST /api/physical/resolve` repeated while `unresolved_remaining` falls, capped at five rounds;
   - `POST /api/recommendations/generate` `{"kind":"radar"}`; on Sundays or with the input set, `{"kind":"discover"}`;
   - the compare and deploy-hook steps from `snapshot.yml`, with `next` added to the compared outputs (optional, like picks and radar).
   A failed refresh or generate step is a warning, not a failure — the next steps run on yesterday's data and the summary says which step failed. A 409 from the catalogue lock (I pressed something at the same time) is reported the same way. `concurrency: nightly`, no cancel-in-progress. The job token is a repository secret.
4. Admin landing (`/admin`): one "Last nightly" line — the latest `catalogue_runs` times and ok/failed from `GET /api/physical/status`, and Radar's and Discover's `generated_at` — so a failed run shows up here rather than as an empty public page. No new table.

**B. The public endpoint**

5. `GET /api/public/next`, registered on the public router in `public_outputs.py` like picks and radar, read-only, pinned by `test_public_outputs.py`. Shape:
   - `generated_at`: `picks` (the day the public picks are from, or null), `catalogue` (the stalest store's last good run, as the admin Radar list reports it), `radar`, `discover` (their last `generated_at`);
   - `tonight`: `up_next` (a `PublicItemCard` for the pinned public item, or null) and `picks` (exactly `load_public_picks`);
   - `wanted`: public items with `wanted`, as `PublicNextRow` with `item_id` set, upcoming ones carrying their release date;
   - `buy_now`, `preorders`, `later`, `not_on_cartridge`: lists of `PublicNextRow`.
   `PublicNextRow`: `title`, `platform`, `physical_format`, `release_date | null`, `release_precision | null`, `cover_url`, `igdb_url`, `reasons` (at most two), `top_pick` (true for a Discover pick), `new` (a full cartridge released within the last 30 days), `item_id | null` (wanted rows only). **Never** `id`, `score`, `rank`, `hypes`, `lane`, `store_lines`, `format_note`, `model_note`, `ranked_by`, a pre-order window, or an answered row. A test walks the whole body and asserts none of those keys appear at any depth.
6. Sectioning is server-side, in a pure module (`backend/next_list.py`, no FastAPI or SQLAlchemy in its imports, tested like `radar.py`): pending Discover picks and pending Radar rows in, `today` in, sections out. The rules are `AdminStoreList.jsx`'s `radarSection` / `buildList` / `periodEnd`, moved: a Discover pick or a released full cartridge → `buy_now` (dedupe by IGDB id and platform, not title); a full cartridge whose period has not ended and starts within 90 days → `preorders`, soonest first; a full cartridge beyond that, or dated to a quarter or year → `later`, capped at twelve; a digital-lane, Game-Key Card or code-in-a-box row → `not_on_cartridge`, capped at twelve. Discover rows that are not released (none should be — "everything dated after today belongs to Radar") are dropped, not shown. Platform grouping (Switch 2 before Switch) is the page's job, not the endpoint's.
7. The same module serves an admin route, `GET /api/recommendations/store-list`, returning the same sections with the private fields added (`id`, `score`, `store_lines`, `format_note`, `release_date` from any source). `/admin/store-list` reads it (see 15), so the two pages can never disagree about which section a game is in.
8. **A public reason names only public games.** Discover already stores `based_on` item ids per pick in `source_metadata`: keep a reason only when every id it rests on is a public item; else drop it; when nothing survives, one genre line from the row's stored `genres` ("Shares Mystery and story rich with games on my shelf"). Radar reasons need the same treatment — either record the reference ids beside the text at generate time (`source_metadata.based_on`, the same key) and filter, or rebuild them at read time from public rows the way `picker.public_reasons` does. Decide in the design; rows generated before the ids existed publish no reason until the nightly regenerates them (fails closed, as `release_source` does). Tests: a pick whose `based_on` includes a private item loses that reason; a row with no surviving reason gets the genre line; every public reason is first person.
9. **A public date is a registry or IGDB date.** `buy_now` rows publish no date (`new` is computed server-side from whatever date is known; a boolean leaks nothing). `preorders` and `later` rows publish `release_date` only when `source_metadata.release_source` is `registry`; a row with only a store's date sorts last in `later` with `release_date: null`. After the first nightly run, count how many rows that hides (check E21); if it is most of them, extend `collapse._release` with IGDB's per-platform `release_dates` for the row's platform — `sources.igdb.parse_upcoming` already reads them for lane 3 — as a fourth source named `igdb_platform`, which is public. A store's date never is, and `igdb_first` stays out (it is the earliest date on any platform).
10. `/api/public/picks` and `/api/public/radar` stay in this phase (the snapshot and the post name them) and are retired in a follow-up once nothing reads them. Note that in the plan.

## Constraints to carry into the spec

- Public pages other than `/spine*` still make no API calls; Home and Projects keep reading the static snapshot.
- Nothing public writes, generates or spends quota on a visitor's action. The job token grants exactly the whitelist, nothing else, and the test for that is the point.
- Store names, prices, stock and pre-order windows stay private; the robots.txt courtesy rule from the showcase review stands.
- Shelf conventions from `CLAUDE.md`: tokens in both theme blocks, `page-wide` via `WIDE_ROUTES`, `role="img"` on non-text marks, nothing hover-only, `useMediaQuery` not `matchMedia`, prefs through `readShelfPref` / `writeShelfPref` with a `shelf.next.*` namespace.
- `content/*.js` stays the single source of copy.
- Pure modules stay pure: `next_list.py` joins `radar.py`, `discover.py` and `picker.py` under the no-framework import rule.
- Commits conventional, ≤5 files, independently valid; ruff + Prettier + ESLint after every file change; both suites green.
- Two PRs: **A** (token, workflow, admin line) first, so there is data when the page lands; **B + C + D** second. E is verification, not a PR.
